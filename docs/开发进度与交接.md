## 1. 这是什么

一个**自用**的 macOS 五笔输入法：Intel Mac、86 版五笔、全本地、不登录、外观要好看。
不是要发布的产品，所以很多取舍是「这台机器好用就行」。

技术栈：

| 层 | 来源 | 位置 |
| --- | --- | --- |
| 引擎 | librime 1.17.0 | squirrel-fork/librime |
| 外壳 | fork 自 rime/squirrel | squirrel-fork |
| 码表 | KyleBing「极点五笔86」 | squirrel-fork/data/plum |

安装位置是 ~/Library/Input Methods/Xpier.app（**用户级**，不是 /Library/Input Methods），
用户配置目录 ~/Library/Xpier（xpier 分支起与官方鼠须管分家；老数据由 update-xpier.sh
从 ~/Library/Rime 全量搬过去），派生数据在 ~/Library/Xpier/build。

## 3. 日常操作（根目录直接跑，不用 cd）

根目录有个只做转发的 `Makefile`（本地文件，不进版本管理，见 7-4）：
环境变量（DEVELOPER_DIR、pip cmake 的 PATH）都在里面配好了。

    cd /Users/admin/Server/Shurufa
    make debug      # 构建，约 60~70 秒；会先跑构建期补丁链
    make package    # 打包（含自检，不过就拒绝出包）
    make update     # 安装（**必须由人执行**）
    make check      # 只读自检：进程在不在、装的是哪一版、码表产物回来没
    make probe      # 不装机验证引擎：KEYS="tzfu tffu zni" make probe
    make requirements  # 装前自检：8 大项，缺什么当场问你要不要装（详见 6.8）
    make doctor     # 出厂质检：装完验“是这次的包吗、输入法接管了吗”（详见 6.8）
    make test       # 不装机验引擎：probe 跑 tffu/tzfu/zni 矩阵断言（详见 6.10）
    make install    # 装到 ~/Library（= install-user；update 是旧别名，必须人执行）

> ⚠️ 工具链（2026-09-17 更新）：以前靠 `/tmp/rimeenv`（cmake+boost，
> 系统清理 + pip/x-boost 路径全烂掉，已废弃）。现在正道是
> `brew install cmake boost`（/usr/local/include、/usr/local/bin），
> librime 两轨（App 轨 build/、探针轨 build-rime）都已验证 configure 能过。
> 根 Makefile 里原来 export 的 `/tmp/rimeenv/bin` 已删掉。
> 如果哪天 librime 编不过，先看这两个链接还在不在，没了就按上面重建。
> 另：`librime/lib/libopencc.dylib`（gitignored）是从
> `librime/deps/opencc/build/src/` 拷过来的，丢了同样拷一份就行。

### 打不出中文时先跑 `make check`

`update` 的第 3 步会删掉五笔编译产物、等下次切回输入法时重建。
重建窗口（约十几秒）内打不出中文是正常的，不是包坏了。
`make check` 会列出 4 个产物在不在、有多大：
全在 → 切回输入法直接打；缺 → 切回输入法等十几秒再 `make check`。
只有 4 个文件都在还打不出，才是真问题。

### 为什么第 3 步必须人工执行

自动化代理的文件沙箱限定在 /Users/admin/Server/Shurufa，写不了 ~/Library：

    $ touch ~/Library/Input\ Methods/.probe
    touch: Operation not permitted

所以安装永远是：代理改代码 → 构建 → 打包 → **人跑 update-xpier.sh**。

### update-xpier.sh 做的六件事（顺序不能改）

1. 覆盖文件（输入法还在跑，不影响）
2. 杀进程（**必须在覆盖之后** —— 反过来的话系统会在文件没盖完时把输入法拉起来，
   新进程读到的还是旧文件，表现就是「换了包却毫无变化」）
3. 删掉五笔方案的派生产物，强制重编码表（改过 .schema.yaml 才需要，见第 5 节）
4. 用**正确路径**重新注册输入源（输入法名字就是在这时候被系统读走的）
5. 刷 LaunchServices
6. 自检：打印两个构建时间做对比

## 6. 这次做完的事

### 6.1 z 万能键（原本完全没有）

五笔 86 的编码只用 a–y，z 空着。用户场景：只记得 t?fu，想输 tzfu 试。

**修之前 tzfu → 0 个候选。** 查证过程：

- table_translator 只拿整串精确查表（table_translator.cc 的 Query 里直接
  dict_->LookupWords(code)），**查询期没有任何通配逻辑**
- speller/algebra 是在**编译词典时**改编码的（dict_compiler.cc:310 起），
  不是改用户输入 —— 「把 z 派生到 a–y」那种写法方向反了，试过，无效
- librime 里没有可用的 lua 插件

**解法**：反过来 —— 给每个编码再派生一条「把某一位换成 z」的别名。
derive 的语义正是「在原有编码基础上增加新的编码」。

只做第 **2/3/4** 位，不做第 1 位：z 打头的输入已被 recognizer 的
reverse_lookup（正则 ^z[a-z]*'?$）整体吃掉用作拼音反查，两者不能同时占第一位。

代价：prism（编码索引）从 650KB 涨到约 8MB，table.bin 不变。

**已知局限**：输 tzzu（两个 z）不行，因为只派生了一个 z 位置。
要支持得再加 C(3,2)=3 条规则，索引会再涨。

### 6.2 z 拼音反查（原本也从来没 work 过）

方案里 reverse_lookup/dictionary 写的是 pinyin_simp，但 schema/dependencies
那一行被上游注释掉了：

    dependencies:
    #    - pinyin_simp

后果：rime 部署时根本不去编译这张码表，反查翻译器运行时加载不到它。
**实测：修之前 zni → 0 候选；修之后 → 你/拟/尼/呢/泥。**

用 dependencies 而不是 schema_list：后者会让 pinyin_simp 变成一个可选输入方案
出现在方案选单里。

### 6.3 候选后面显示五笔编码

需求：用万能键时要知道正确编码，才能记住。

先反编译了编译好的码表（rime_table_decompiler），确认里面**根本没有注释这一列**
（每行只有：词条、编码、权重），DictEntry.comment 始终为空 ——
所以 translator/comment_format 无论怎么写都变不出编码来。

**解法**：reverse_lookup_filter —— 拿候选文字回主码表反查编码再写进 comment。
纯配置：

    engine:
      filters:
        - simplifier@tradition
        - reverse_lookup_filter@wubi_code

    wubi_code:
      tags: [abc]
      overwrite_comment: true
      dictionary: wubi86_jidian

实测：

    输入 tzfu →  徒劳无益 tafu / 等 tffu / 徒增 tffu / 生境 tgfu / 处境 thfu

**行为定稿（2026-09-14）**：wubi_code 块加了
`show_if_input_contains: "z"`，引擎侧 `ReverseLookupFilter::AppliesToSegment`
（librime 3ed4743）只在段输入**任意位置**含 z 时挂 filter。
rime_probe 实测矩阵：tffu/ni 完全干净；tzfu/tfzu/tffz/zni 显示编码。
无 z 时的干净是 filter 级保证 —— table_translator 本来就不产出 comment，
反查翻译器只处理 z 开头输入，所以门一关就什么都不显示。

> ⚠️ 教训：librime 改完只编 `build-rime`/`build` 不够 —— Xcode 链接的是
> `lib/librime.1.dylib`（`make librime` 才更新它）。曾经因此老引擎进包，
> `show_if_input_contains` 被静默忽略、编码常显。以后改完引擎必须走
> `make librime`（App 轨，静态 opencc）+ 重打 App 包，并用
> `strings lib/librime.1.dylib | grep <新符号>` 确认进包。
> 注意：`make librime` 要 cmake 在 PATH 里（`brew install cmake`，
> 以前靠 /tmp/rimeenv，已废弃）。直接进 squirrel-fork 跑，
> 报 cmake 找不到就是没装 —— 这是环境问题不是代码问题。

**单字漏码（2026-09-15 修，librime b61e2a5）**：门控值原来在 `Initialize()`
里读，而建菜单调 `AppliesToSegment` 在前、取候选调 `Apply→Initialize` 在后。
首个输入的第一次构菜单永远看到空值，空值按「不过滤」处理 → 单字输入
（首构即终构）漏码；多字输入终构时值已加载所以干净。且段状态 kGuess 后不再
重翻，漏上的码一直挂着。修法：跟 `TagMatching` 的 tags 一样，构造时就读好。
另：`show_if` 为空=「没配门控」时保持常显（上游默认语义，别动）。

### 6.4 配置路径解析错误（改动最大的一处）

parseFile 用「一个 sub 字符串 + 缩进判断」表示嵌套，而且 schema 层那份代码
无视缩进、只要 sub 非空就往路径上拼。部署后的方案文件正好把两个坑都踩全：

    translator:
      comment_format:      # ← sub 被设成 comment_format
        - "xform/.+//"
      dictionary: wubi86_jidian   # ← sub 没清掉

于是 translator 段全部 7 个键的路径变成 translator/comment_format/dictionary
这种**不存在的键** —— 写回配置时 Rime 直接忽略，用户看到的现象就是「改了没反应」。

同病的还有 reverse_lookup/prefix|suffix、key_binder/import_preset、
punctuator/import_preset。

另外两处：

- 顶格标量（config_version: 0.50）不会重置 section，被挂到上一个段落名下；
  而 keyboard_layout / chord_duration / show_notifications_when 是**真实设置**，
  以前被错误地归到 preset_color_schemes / app_options 底下
- 引号判断写在 yamlUnquote **之后**，于是 "[A-Z][-_.0-9A-Za-z]*" 解码后以 [
  开头被当成流式集合丢掉 —— recognizer/patterns/uppercase 和
  style/candidate_format 因此从来没在界面上出现过

改成**容器栈 + 按缩进出栈**；引号判断提到解码之前；加了跨层去重。
**结果：425 项 → 398 项**，其中 27 条是去掉的重复、5 条是新找回的真实设置。

### 6.5 设置界面

- **6 个标签页**（外观 / 输入·按键·方案 / 标点与简繁 / 反查与造词 /
  主题配色 / 常用 APP 关联），共 398 项，全部可编辑。
  标签上不带条目数（以前带「外观 22」这种后缀，用户反馈不要）。
  外观页卡片顺序：字体与主题 / 候选窗布局 / 显示方式 / 候选窗外观 /
  菜单栏与提示 —— 这个顺序是按瀑布流落列定的，显示方式和提示落在右侧。
- **主题配色页**：默认只渲染选择卡（主题下拉＋复制主题＋三行预览）
  与所选主题（当前使用的带★置顶，之前置顶逻辑有 bug 从没生效过），
  不再一次建 287 个控件，打开不再卡，切主题先写回内存再只重建本页。
  内置主题的名字/作者锁定只读，「复制主题」得到全可改的自定义主题
  （保存整组落盘 custom.yaml，部署后出现在下拉里）。
- **卡片**：自己画的圆角描边 + 标题压在上边线上。
  原来用 NSBox(.primary) —— 现行 macOS 上它**根本不画边框**，
  卡片区域除了一行标题之外什么都没有（这就是「标题不在边框中」的真正原因）
- **高度实测**：两遍走，先建出来用 fittingSize 量真实高度，再瀑布流落位。
  原来是「行数 × 30 + 36」估的，比真实值大 30pt，卡片底部空出整整一行
- **一律半宽**，数量是奇数时最后一块占半边，不硬撑整宽
- **基线对齐** grid.rowAlignment = .firstBaseline；自定义滑杆/步进器要自己
  实现 firstBaselineOffsetFromTop，否则网格只认它们的底边（读数会低 7pt）
- **行距 10**、**标签字号 13**（与控件同号）
- **不让用户手打**：新增 pick 类型，候选值从运行环境枚举 ——
  系统字体族（过滤掉不支持中文的）、本机已编译的码表、可继承的预设文件
- **主题颜色是 ABGR，不是 ARGB**：Rime 配色值 0xAABBGGRR（证据：谷歌主题
  高亮 0xCE7539 = Google 蓝；Solarized 品红/青只在 ABGR 下对得上）。
  上游 SquirrelConfig 按 ABGR 解析（打字窗一直是对的）；本项目的
  XpierColor（设置预览）和 xpier_default/dark 的值一度按 ARGB 写，
  把淡紫 0xffb8aaff 活生生渲染成粉 —— 用户拿着截图问为什么对不上。
  修法：xpier 两主题 18 个色值 R/B 对调 + XpierColor 改 ABGR（含取色器写回）。
  教训：饱和色才看得出字节序反了（近白/近黑对称，错了也看不出来），
  以后调主题先拿谷歌蓝这种不对称色标尺验一遍解析。
  另：改完值要用户端重部署 build/squirrel.yaml 才生效（增量部署会刷；
  若颜色没变，让用户点一次「保存并部署」）。
  2026-09-15：用户钦定粉色为默认，xpier_default 的选中候选背景改回
  0xffb8aaff（按 ABGR 读正是那块粉 (255,170,184），和规范不冲突）。

### 6.6 输入法菜单

和「设置…」平级加了三个开关：**输简出繁 / 全角标点 / 英文标点**。
名字按「勾上之后是什么」取，不照搬 zh_trad / full_shape 这种开关名。
- 全角和英文标点是正交的两维（形状 vs 标点集），不互斥，各管各的。
- 曾经有第四个「生僻字」（extended_charset），后随字符集过滤默认关闭而删除：
  五笔精确码不需要这层过滤，放个摆设按钮不如删掉。想滤回常用字去设置开
  「只出常用字」，再用 Ctrl+` 切。
- 生僻字默认可打的另一半：字必须在码表里。𡋤（U+212E4）主码表没有，
  已加进个人码表（wubi86_jidian_user.dict.yaml，fnyu=土f+尽一n二y+尽末u，
  对照赆=mnyu/烬=onyu；结构 ⿰土尽 由 cjkvi-ids 确认）。探针实测默认状态
  fnyu → 真心诚意、𡋤，jyu → 旻，qpwk → 镕。
- **菜单开关点了白点（2026-09-15 修）**：三个叠加的 bug。  其一，`zh_trad` 写了 `reset: 0`，而 librime 建引擎是先读存档
  （RestoreSavedOptions）再强制复位（InitializeOptions，engine.cc 即此顺序），
  等于每个新输入框都把繁体掰回简体 —— 已删掉该 reset（ascii_mode 的保留，
  进新框回中文是故意的）。其二，菜单调的是 `set_option` API，只作用当前会话，
  librime 只在走 switcher 选单那条路才落盘；且菜单栏无焦点点开时根本没会话，
  原代码直接 return，点了等于没点。现在菜单双写 user.yaml（var/option/<名>，
  行级合并），有会话就地生效、无会话下次打字生效；显示也没会话时读存档。
  其三（最阴的），开关项用的带参 action（`toggleSwitch:`）会被
  TextInputMenuAgent 跨进程派发静默吞掉 —— 不崩溃、无日志、点了没反应。
  上游所有菜单项都是无参 action，唯一能点的「设置…」也是。改成一开关一无参
  方法后全活。教训：IMK 菜单项只用无参 @objc action；private/internal 倒不影响。
  排查时往 /tmp/xpier-menu.log 写面包屑定的位（统一日志里 Squirrel 零记录）。
- **拔掉 Ctrl+Shift+数字 暗门（2026-09-16）**：上游 `numbered_mode_switch` 预设
  （Ctrl+Shift+2/3/4/5 切 ascii/full/simplification/extended）是另一套平行开关，
  在终端复用器里随手误触：不落盘、不经过菜单，菜单勾和实际对不上；
  其中 simplification 还是死开关（simplifier 认 zh_trad，它没人读）。
  构建期 `patch_key_binder.py` 从 default.yaml 摘掉该引用（翻页/Emacs 组保留），
  菜单是唯一控制面。教训：凡是不落盘、不显示状态的开关都是未来的灵异事件。
  后续（2026-09-16）：用户要求快捷键可见可控 —— 快捷键回到应用侧实现：
  `handle()` 里纯 Ctrl+Shift+3/4 直接进 `flipSwitch`（与菜单同一条路），
  菜单标题明示 `⌃⇧3/⌃⇧4`（只写字，不设 keyEquivalent，设了会劫持宿主 App）。
  3=全角形状、4=输简出繁（对齐 Rime 传统键位；4 原来绑的是死开关 simplification，
  现在名副其实）。5 不绑（extended_charset 已无意义，空出来还宿主）。
- **引号配对开关（2026-09-16）**：半角 `"`/`'` 默认成对（现状），关掉后空闲时
  直出单个（写代码、敲命令不断行）。实现是应用侧拦截（`handle()` 看字符，
  非 US 键盘也认得），只在无构词+半角时直出，构词中和全角里一律走引擎配对。
  状态走自定义 option `quote_pair`（引擎不读，只当存身；逻辑默认开=现状，
  `switchLogicalDefault` 记 + `createSession` 里种 + `save_options` 持久化三件套，
  以后凡是「默认开」的自定义开关都照此办）。教训：Rime option 默认全关，
  默认开的语义只能应用侧补。

**踩过的坑**：菜单项**严禁设置 keyEquivalent**。输入法菜单会被 IMK 插进宿主 App
的菜单栏，其快捷键先于 App 自身菜单匹配 —— 曾经用 Cmd+, 导致**所有 App**

### 6.9 自定义短语（2026-09-17，用户选了“本机+gzip 拉取”）

  `mai` 这种前缀联想里也能混排第二。
- **缺文件必须有桩**：`import_tables` 引用的表若随包/用户两边都没有，

- **gist 拉取还没做**：定的是设置页填 gist 地址、保存时拉下来合并到用户文件

### 6.11 干净树验证挖出的三个雷（2026-09-18，快照包实测）

把快照包解到空目录跑 `make && make test`，连跪三次，全是
“开发树永远不炸、新机器必死”的病：

1. **`cp rime-plugins` 拷不存在的目录**：cmake 只定义了插件目录变量名，
   从没真正安装它；开发树里那个空目录是 9 月 4 日的陈尸。
   修法：`copy-rime-binaries` 改成 `mkdir -p lib/rime-plugins`。
2. **Sparkle 目标写死 `git submodule update`**：快照包没 `.git` 直接死。
   修法：源码在就跳过，只有 git 树才拉（requirements.sh 的无 git 分支同理）。
3. **工程里 22 个幽灵插件引用**：`package/add_data_files`
   每次构建都把 `lib/rime-plugins/*` 的文件名 bake 进 pbxproj，
   9 月 4 日那批 0 字节占位文件（Makefile、Squirrel.xcodeproj 等仓库根文件名）
   就这么永久进驻了；连已装包的 Frameworks 里都带着这些 0 字节垃圾。
   修法：工程里 69 行全删（只剩空 phase 外壳），脚本只收真实存在的
   `*.dylib`，`lib/rime-plugins/` 垃圾清空——五笔方案根本不用
   lua/octagram/predict（schema 无引用），插件纯属陪葬。
4. **`set -e` + 空数组赋值静默自杀**：上面把目录搞空之后现形。
   `lib_files=($(for ...; done))` 的退出码等于替换体最后一条命令的；
   目录空时最后一条是失败的 `[ -f 字面量 ]`，脚本被毙还不打印。
   修法：循环尾加 `; true` 兜底。

四连修完，干净树 `make`（自检 13 项）+ 打包验收（14 项）+
`make test`（探针 3/3）全绿，退出码 0。教训：发布前必须在干净目录
从零跑一遍全流程，开发树的陈年构建产物会掩盖一切。

### 这次踩过的坑（代码注释里都留了记录）

- **NSBox(.primary) 不画边框** —— 别指望它做 fieldset
- **cacheDisplay 的产物是透明底**，且合成白底必须用纯 CoreGraphics；
  NSGraphicsContext.current + NSRect.fill() 在离屏场景下**静默无效**
- **窗口挪到屏幕外再 orderFront，AppKit 会跳过整窗绘制**，截出来只有边框
- **只设 window.appearance 不管用**，绘制时取的是 NSApp.appearance
- **grep 对多字节 UTF-8 字面量不可靠** —— 同一个二进制 grep 查某中文串得 0，
  python 数出来是 1。判断用 python 读字节
- **shell 里 cut/awk 处理多字节字段也不可靠**，统计一律用 python
- **shell heredoc 里的 Python 不要用反斜杠 n 转义** —— run_code 的 JS 模板串
  会把它变成真换行，脚本直接语法错误。把 Python 写成文件再跑（String.raw）
- **git commit -m 的信息里含引号会打断 shell**，用 -F 文件
- **改函数用整函数替换**（按花括号配对定位），不要读 N 行拼 old_string ——
  那样会把下一个函数的头一起截掉（犯过 3 次）
- **补丁脚本判定段落边界时要跳过注释行** —— 上游那句被注释掉的依赖是**顶格**的，
  按「顶格即段落结束」去扫会把它当成边界，目标行于是落在切片范围之外、永远改不到
- **bash 3.2（macOS 自带）里 `$NAME` 后面不能直接跟中文** ——
  `$XCODE_VER（要 14+` 会被当成名为 `XCODE_VER（要` 的变量，`set -u` 下直接
  unbound variable。凡是后面跟全角字符的变量一律写 `${XCODE_VER}` 花括号。
  requirements.sh 修过一次，reregister.sh 里 `$TIS）` 同病一起修的。
  查漏命令：`grep -rEn '\$[A-Za-z_][A-Za-z0-9_]*[^ -~]' scripts/*.sh`（命中且没
  `${}` 的就是雷）。另：`$(4 - $N)` 在 `set -u` 下是命令替换不是算术，
  要写 `$((4 - N))`
- **git submodule status 前缀别用 grep 判** —— 空格=一致、`-`=没 checkout、
  `+`=SHA 对不上。requirements.sh 用 case 三分支分别报，免得“一致”被误报成没 checkout
- **`make check` vs `make doctor`** —— check 是日常自检，doctor 是出厂质检
  （多“装的是这次的包吗、输入源启用了吗”）。修包验证用 doctor，别往 check 里
  无限加项
